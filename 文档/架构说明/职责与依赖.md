# 职责与依赖

## 一次加载资料的流程

1. 用户在 `feature/profile/ui` 的页面发起操作。
2. 页面状态持有者调用 `feature/profile/data` 的数据仓库；规则复杂时，可先调用 `domain` 中的用例。
3. 数据仓库协调远端接口和本地来源，使用 `core/network`、`core/database` 等公共能力。
4. 数据或错误返回后，界面更新显示。

这是未来的示例流程，目前没有实现个人资料加载。

## 新文件放哪里

| 你要写的内容 | 放在哪里 |
| --- | --- |
| 登录按钮事件、登录页状态 | feature/auth/ui |
| 复杂且可复用的登录规则 | feature/auth/domain |
| 登录请求的数据仓库、响应转换 | feature/auth/data |
| 多个功能共用的网络客户端 | core/network |
| 设置开关读写 | feature/settings/data |
| 通用偏好读写底层封装 | core/preferences |
| 首页布局 | res/layout，以清晰英文前缀区分功能 |
| 只在调试时使用的资源 | src/debug/res 的对应资源子目录 |
| 页面设计草图 | 设计资料/页面原型 |

`domain` 是按需引入的层，不要求每个按钮都绕一层。业务功能数据仓库放在该功能内；底层通用设施放 core。复杂应用也可能把跨功能共享的数据仓库提为独立数据包或模块，等真实需求出现再拆分。

不要让网络客户端依赖 Activity。不要让某个公共工具包反过来调用具体业务页面。不同功能之间通过明确的共享契约或导航约定协作，避免随意跨包引用内部类。

## 目录不会自动实现功能

当前未添加网络库、数据库库、ViewModel 库或依赖注入框架。预留目录里的文件名只说明未来的放置位置，不代表对应类已经存在。测试目录也尚未配置测试依赖和设备测试运行器。
